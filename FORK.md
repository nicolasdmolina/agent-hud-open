# Fork notes

This is a private-use fork of [jazzenchen/agent-hud-open](https://github.com/jazzenchen/agent-hud-open). All of the fork's changes live on the branch `fork`, which is the default branch here. `main` mirrors upstream and never carries fork commits. Pull requests target `fork`. Nothing is sent upstream.

## Hermes live channel

Design for tickets 12 to 16. The pure half is built (ticket 12), and so is the connection (ticket 13, "The connection, as built" below).

### Shapes

All in `src/crates/agents/src/hermes/gateway/`, with no I/O and no clock.

- **Where something happens** (`machine.rs`, `identity.rs`). `Machine` is `This` or `Far(key)`. `machine_key(install_id, root_home)` is the only way to a key: the first 16 hex characters of the SHA-256 of the install id, a line feed and the far root home. It gives no key and a reason (`NoKey`) unless the id is exactly 32 lowercase hex characters, which is what Hermes writes, and the home is written as a canonical path is. Nothing stands in for a missing id, a connection entry's id least of all, and no value holds the raw id, so it is in no id and no `Debug` output. `identities_agree()` says whether every gateway found on one route reports the same install id; a route where they differ leads to no one machine. **The root home rule.** A root home is accepted only in the one form a canonical path has: it starts with `/`, names at least one folder, and has no ending slash, no doubled slash, no `.` or `..` folder and no NUL. `/srv/hermes/`, `/srv//hermes`, `/srv/./hermes`, `/srv/x/../hermes`, `//srv/hermes` and `/` are all refused (`NoKey::Home`), never tidied, so one folder cannot get two keys. The model reads no disk and cannot resolve a link: whoever hands a home over (tickets 29 and 30) resolves it where the home is, as `realpath` does, and hands over that exact text every time. The same rule holds for the root given to `anchor()` and `Profile::in_root()`. `GatewayId` is a machine and an anchor profile, and stays the same across the gateway's restarts. `anchor(root_home, served homes)` picks the anchor: the default profile if the gateway serves the root, else the named profile whose home sorts first, whatever order they are listed in. It is given the root because a home's own path cannot say which profile it is: a root may itself lie in a folder called `profiles` (`/srv/profiles/work`). `Profile::in_root(root, home)` is the default profile at the root, a named one at `<root>/profiles/<name>`, and nothing anywhere else; a served home that is no profile of the root is left out of the choice. A gateway is written `local` (this machine, default anchor; phase 1's one gateway), `local/<anchor>` (another gateway on this machine) or `<key>/<anchor>` (a far one). `Profile` is `Default` or `Named(ProfileName)`. A `ProfileName` can only be made of a name Hermes allows (`hermes_constants.PROFILE_ID_RE`): 1 to 64 of `a-z`, `0-9`, `_` and `-`, starting with a letter or a digit, and never `default`. `Profile::named()` and `Profile::folder()` give none for anything else and tidy nothing, so no profile holds a slash or a colon. `SessionRef` is gateway, profile and the gateway's session id, made by `SessionRef::new()`, which gives none for an id that can be no session's: an empty one, or one with a slash before its first colon. `hud_session_id(machine, profile, id)` is the one function that builds a HUD session id, for `SessionRef::hud_id()`, the hooks and the `state.db` reader, and refuses the same ids: `hermes:<id>` and `hermes:<profile>:<id>` on this machine, `hermes:<key>/<profile>:<id>` on a far one, the profile always written, `default` too. **Why a far id is never a local one.** Between `hermes:` and the next colon, a far id holds a slash (after its key) and an id of this machine never does: a profile's name holds none, and a session id that would put one there is refused. That holds for whatever a hook payload, a `state.db` row, a folder name or a gateway's list hands over: a hook that names a malformed profile or session reports nothing, a `state.db` row with such an id is left out, a listed session with such an id is not followed, and a folder that is no profile's name is never taken for one (below). Every id Hermes itself writes is what it was, byte for byte. The gateway is no part of a session id: two gateways on one machine with the same profile and session id name the same session, and a profile can move between them. Request ids keep their form, `hermes:<gateway>:<profile>:<session>:<asked>`, with the gateway written as above, so two gateways never share one. The reader builds this machine's ids, and a mirror's far ids through `stored_session_id(stored key, profile, id)`, which writes through the same hand, so a stored session and a live one are one id. **A stored key** (`StoredKey`, ticket 23) is a key read back from a file Agent HUD wrote: exactly 16 lowercase hex characters, nothing tidied. It names stored sessions and proves nothing, so there is no way from it to a `MachineKey`, a far `Machine` or a `GatewayId`; only `MachineKey::stored()` goes the other way. **A home always has a profile; only a named value is checked.** `Profile::of_home(home)` is how the hooks (`HERMES_HOME`), the `state.db` reader and `identify()` name a home by its path alone, as phase 1 did: a home whose last two folders are `profiles/<name>`, with a name Hermes allows, is the named profile `<name>`, and every other home is the default profile of the root it is. So `HERMES_HOME` can be any folder (`/srv/profiles/Work`, `/srv/profiles/.hermes`, `/opt/hermes`): it is followed, read and reported, as `hermes:<id>`. The grammar is checked where a profile is named by a value: `Profile::named()`, a hook payload's `profile` field, and `hud_session_id()` through the `Profile` it is given. A payload that names a malformed profile reports nothing, whatever its home. **What is left open.** By its path alone, a custom root that is itself at `/x/profiles/<valid-name>` reads as the named profile `<valid-name>`, not as a root's default profile. That is how the ids already saved in the ledger were made (`hermes:work:s1`), so it is kept: changing it would move saved history to a second namespace. Ticket 26 keeps that everywhere: a gateway's sessions, cards, request ids, waiting flags and live states are named by the home's path alone, exactly as the hooks and the reader name them, so one session is one row (`core/src/tests/hermes_identity.rs`), and every call is routed by that same name. That is also what Hermes does: it takes the folder above `profiles` for the root of such a home, so a home at `/x/profiles/work` is the profile `work` to it, and a call for `default` is refused as `profile_mismatch` (`hermes_constants.py`, `_hermes_root_of`; `hermes_cli/profiles.py`, `get_profile_dir` and `profile_matches_home`; the second PR review of ticket 26 traced it and ran it against a real 0.22.5 gateway, `evidence/26/verifier-files-2/`). `identify()` is not told the root. The root home of the machine, as Agent HUD is configured, picks one thing: the anchor a gateway is named by (`anchor()`), so the gateway that serves the configured root is `local`, as in phase 1. The first two versions of ticket 26 named, and then routed to, such a root as `default`; both PR reviews caught it. **A profile folder ending in a line feed is not a named profile** (ruling on the second review's finding 2). Python's `$` lets Hermes's own pattern match `work\n`, so Hermes would list and serve a folder of that name if one existed. Hermes never creates one: creating a profile strips whitespace. Letting a line feed into session ids and log lines is the greater risk, so the name is refused as a named profile and no code was changed for it. Such a folder falls under the rule above like any other folder that is no profile's name: it is read as a default profile, and no id holds its line feed.
- **Connection state** (`connection.rs`). `Disconnected`, `Connecting`, `Ready(Instance)`, `Unsupported(reason)`, `Failed(reason)`. `identify()` reads the control socket's answer with the checks Hermes's own client applies, and one of its own: an origin that is not plain `http` on this machine is `Unsupported`. A new `instance_id` is a restart.
- **Pending item** (`ask.rs`). `Pending` is a `SessionRef`, an `Ask` and `wait_ms`: how long Hermes said it waits for an answer. Hermes says how long and not since when, so when the wait ends is never known. `wait_ms` is for a card to say. No card closes on a timer of Agent HUD's own. `Ask` is one of three types. `Question` has a prompt id, the turn's `execution_generation`, the text, the choices and whether several may be picked. `Approval` has a prompt id, the generation, the command, the description and only the choices Hermes offered. `Batch` is the set of questions Hermes sends as a request of its own (`clarify`, id `srq-…`) when the terminal UI started the turn. It has a request id and ordered questions, each with what another viewer already answered or skipped, and no generation and no deadline.
- **Decision** (`decision.rs`). `Question::answer(Answer)`, `Approval::respond(Choice)` and `Batch::answer(answers)` are the only ways to build an answer, so an approval's choice cannot be put on a question. A doc test proves it does not compile. `Answer` cannot be empty, and a question is never skipped: Hermes has no skip a viewer can send for one question that holds on every runtime. `Batch::answer` always settles the set: questions not answered here and not locked by another viewer go as `null` (skipped). `Pending::reply(decision)` turns the HUD's `RequestDecision` into the exact frame. `allow` is `once`, `deny` is `deny`, `always` is `always`, and `always` with `suggestion: {type: "scope", scope: "session"}` is `session`.
- **Card** (`card.rs`). `Pending::view(now, machine)` is the usual request view; a far machine's label, when given, is its `machine`, and without one the card has no `machine` at all. An approval lists the lasting choices Hermes offers in `suggestions`, so a limited request shows once and deny alone. Each question of a set has `lock`: null, `{state: "answered", answer}` or `{state: "skipped"}`.
- **State** (`state.rs`, `poll.rs`, `fold.rs`, `reconcile.rs`, `effect.rs`). `Gateway::poll()` begins a poll. The `Poll` says which calls to make (`steps()`) and takes their results (`answer`, `failed`). `Gateway::apply(Input, now_ms) -> Vec<Effect>` takes the finished poll and everything else that happened: identify answered, the socket was lost, an answer was sent or replied to. Effects are what to do: open a card, change it, close it with the reason, show it again, poll now.

A card closes when a poll finds its request settled, its turn over, its set of questions no longer open, or its session gone from the live list; when an answer to it comes back `resolved`, `already_resolved` or `stale_generation`; and when the gateway restarts or turns out not to have the live connection. A dropped socket closes nothing: the request still waits in Hermes. Time passing closes nothing.

### How the cards follow Hermes

The cards follow polls. A poll asks Hermes what waits now, and the model opens, changes and closes cards until they match. Nothing read in one poll is carried into the next. The first two state layers treated every reading as an event to merge into remembered state, and every order of delivery became a bug (`evidence/12/verifier-report.md`, `verifier-report-2.md`). This one has nothing to merge.

- **What is kept between polls.** The open cards, each keyed by gateway, profile, session and the gateway's own request id. The gateway's instance id. A count of polls. When a snapshot was last taken of each waiting session (see below); that is the one thing a poll leaves for the next beside the cards. Also what the last poll listed each session as doing, which is only reported (`statuses()`, `poll_ms()`) and never read by a poll. No cursors, no epochs, no record of what was over.
- **One poll.** `session.active_list` for every served profile. Then each session that works or waits or shows a card is read with `session.events.since`: once without an epoch, which Hermes always answers empty with the stream's epoch and latest event, and then for the events. Each reply also lists the sets of questions open now (`open_requests`). None of this subscribes. Sessions that are idle or starting and show no card are not read.
- **The fold** (`fold.rs`). From one gap-free run of events in the gateway's order: a request waits from its request event until an event says it settled. A `message.complete` takes every request of its turn and of earlier turns, wherever the request event stands in the run. A later turn's `message.start` takes the requests of earlier turns. A session that runs no turn (listed idle or starting) keeps no card. The sets of questions are whatever `open_requests` lists. A question or an approval that Agent HUD cannot show (a kind Hermes adds later) gets no card, and no snapshot either.
- **The poll reads from the oldest event Hermes still keeps.** Hermes keeps the last 512 events and 4 MiB of a session's stream. It answers a read whole if it starts no earlier than the last event it dropped, and refuses it otherwise (`tui_gateway/event_replay.py`, `is_truncated`; `gateway/session_events.py`, `since`). One short turn is about 24 events, so a read from 0 stops working a few turns in and never works again for that stream. The refusal says where the stream ends and not where it begins, so the poll searches for the oldest event it can read (`read.rs`). It first reads from where that is if only the count made Hermes drop anything: 512 before the latest, or 0. That is usually right, for 2 calls in all. If Hermes refuses (it also drops by size), the poll asks whether the very last event is kept and then halves the range between what was refused and what was answered. On a stream that stands still the search ends on the last event dropped, in at most 12 calls, and every request whose event can be read is seen.
- **A search that does not finish.** A session gets at most 16 calls in one poll. A stream that keeps moving under the search can use them up before the oldest event is found. The poll then knows it has not read everything. It closes no question or approval card of that session on what it did read, opens what it found, and takes a snapshot if one is due.
- **What no read can show: a snapshot.** Hermes lists a session as `waiting` exactly while a question or an approval waits in it (`gateway/session_active_list.py`, `_status`). A request asked before the oldest event read shows in no read, whatever else is seen waiting. Only a snapshot lists it: `session.resume` on a socket of its own, closed after the reply. Its `prompts` and `open_requests` are what waits. A session that does not wait is never snapshotted: no question or approval waits there. A waiting session is unsure, and a snapshot is wanted, when any of these holds: Hermes has dropped events of its stream; the search did not finish; nothing in its events is waited on; a card shows whose request and whose end are both missing from the events.
- **When a wanted snapshot is taken.** At once, if the model has no record of one for that session. Otherwise 30 s after the last (`SNAPSHOT_EVERY_MS`), counted from the time of the poll before. The record is dropped, so that the next poll takes one at once, when a poll lists the session as not waiting, when any card of the session closes (answered here or seen over by a poll), when the socket is lost, and when the gateway restarts. A snapshot that fails leaves no record. Between snapshots, a card the events do not speak for stays as it is.
- **What that costs.** A session whose stream has dropped events, which is any session past 512 events, takes one snapshot when it starts to wait, one after each of its cards closes while it still waits, and one every 30 s for as long as it goes on waiting. A session that has dropped nothing takes none.
- **What a snapshot does to the session.** `session.resume` subscribes. It returns the whole message history, cancels a pending close of the session, lets its background work start again, and keeps the session alive while that socket is open (ticket 11, answer 2). On an idle session it also re-commits the session's settings. A snapshot is only asked for of a session listed as waiting, which is busy and so keeps its settings. But the list is a moment earlier than the snapshot: if the request settles and the turn ends in between, the session is idle when `session.resume` runs and its settings are re-committed. The same holds for the short socket an answer is sent on.
- **Stale polls.** A poll carries the count it was begun with. The count moves when a poll begins, when an answer comes back `resolved`, `already_resolved` or `stale_generation`, when the socket is lost and when the gateway restarts. A poll whose count is not the current one when it comes back is dropped whole. So a poll that read "still waiting" just before an answer landed cannot reopen the card, and a poll of a gateway that has restarted since cannot fill it again.
- **What a poll could not tell.** If a profile's list fails, or a session's read or snapshot fails, the cards concerned stay as they are and the next poll asks everything again. There is no retry state to get stuck in.
- **Approvals settle late.** When nobody answers an approval, Hermes stops waiting but publishes `approval.settled` only when something next asks what waits, or at the end of the turn (ticket 11, answer 3). The card stays until a poll sees that, the turn ends, or an answer given on the card comes back `stale_generation` or `already_resolved`. From source, the poll's own `session.active_list` makes Hermes publish it sooner (`_status` calls `PendingControls.snapshot`, which settles what is no longer active). That was not measured.
- **Deadlines.** `timeout_s` is a length with no start. The model keeps it as `wait_ms` for a card to say and never closes a card on it.
- **Sets of questions.** A poll that lists a set already shown, with different answers from other viewers, changes the card in place (`Effect::Changed`). Nothing replies to the answer to a set, so a set still listed 5 s after its answer was written is shown again (`Effect::Unanswered`); that closes nothing.
- **What can still be missed, and for how long.** A request that waits and that no read shows gets its card at the next snapshot of its session, so it can stay hidden for up to 30 s plus one poll. Three ways it happens. A missed change: the session stopped waiting and started again between two polls, with nothing to close and no lost socket to say so, and the new request's event is already dropped. The whole ring dropped: Hermes keeps 64 streams and 64 MiB across all sessions, so other sessions' activity can drop this one's events with no burst of its own. A moving stream: the search ran out of calls before the oldest event. The same bound holds the other way: a card whose request ended with no event left to say so, in a session that still waits on something else, stays up to 30 s.
- **Cost.** Folding a full stream (512 events, 4.2 MB as JSON) and settling the cards takes about 0.07 ms in a release build and under 1 ms in a debug build; parsing that reply takes 1 ms and about 25 ms (`tests/cost.rs`, MacBook, under load). So each poll reads again everything Hermes keeps of each busy session, and nothing is read incrementally. This measures the model's part only. It does not measure Hermes serving the calls, the extra calls of a search (up to twice the stream's bytes when Hermes dropped by size), or a snapshot, which returns the session's whole history and comes as often as "What that costs" says.

### Shell hooks: kept

The hooks stay installed for running and finished. They are pushes that already work and are tested, and they are all there is for a gateway without the live connection (the Mini's 0.21.6 today). The live connection adds what hooks cannot: the text of a question and a way to answer. Holding a subscription on every session to replace the hooks would change how Nicky's sessions end and re-commit idle sessions' settings (ticket 11, answer 2).

### What ticket 13 must implement

The connection goes in `src/crates/platform/src/clients/hermes/`, started from `hooks::configure` when `clients::runs(&agents::hermes::GATEWAY)`. It owns one `Gateway` per gateway (`GatewayId::new(Machine::This, Profile::Default)` in phase 1, written `local`), feeds it every input and carries out every effect. It decides nothing else.

1. **Find the control socket from a Hermes home passed in.** `<home>/gateway.sock` (`CONTROL_SOCKET`). If that is missing, read `<home>/gateway.sock.path` (`CONTROL_POINTER`) and pass its text to `pointed_socket()`. Check that the home, the pointer and the socket are the user's own with no access for others, and that the listener is the same user. Production passes the resolved `HERMES_HOME`, else `~/.hermes`. Tests pass an isolated home with its own gateway. Never test against `~/.hermes`: adding a profile there rewrites Nicky's `config.yaml` (ticket 11, deviation 1). Resolve links in the home before calling `identify(answer, home)`, which compares it as written.
2. **Handshake.** Send `identify_line()`, one JSON line in and one out, and give the answer to the model as `Input::Identified`. Retry once on a timeout before `Input::Lost(Unreachable)`. On `Ready`, send `ticket_line(instance, Scope::Host)` (it has no `subject`), read the answer with `granted()`, and dial `ws://` and `SOCKET_PATH` under `instance.origin` with `ticket.subprotocols()`, no `Origin` header and no proxy. `identify()` has checked that the origin is plain `http` on this machine, IPv4 or IPv6. Any other origin (`https`, another host) is `Unsupported(Origin)`: it is left to the hooks, no ticket is asked for and nothing dials. There is no TLS. Phase 1 is the local gateway, which serves plain http, and phase 2 reaches a far gateway through a port of this machine forwarded over SSH, which is plain http too. Check the echoed subprotocol is `SUBPROTOCOL`. A refusal goes in as `Input::Denied`, HTTP 403 as `Input::Lost(TicketRefused)`. Allow frames up to 8 MiB.
3. **Tickets are never kept.** Mint, dial, drop. A ticket lasts 30 s and opens one socket. `Ticket` prints as `<masked>`; do not log the subprotocol list.
4. **Wait, do not fall back, while a gateway starts.** `Connecting` after `Identified::Wait` means ask again with backoff. `Unsupported` means stop and leave Hermes to the hooks; ask again rarely, since an update can add the connection. A draining gateway that waits for its turns (`instance.draining`) is `Ready` and can be answered.
5. **Run polls, one at a time for each gateway.** `gateway.poll()` begins one (None unless the gateway is ready). Ask `poll.steps()`, send each as `step.command(Scope::Host).frame(id)`, and give each reply's `result` to `poll.answer(&step, result)`. Call `poll.failed(&step)` for an error reply, a timeout, or a profile that answers `profile_mismatch` or `runtime_draining`. Ask `steps()` again until it is empty, then `gateway.apply(Input::Polled(poll), now)`. The steps of one round do not depend on each other and may be sent together. Never begin a second poll of a gateway before the first was given back or dropped: the model drops the older one, and its calls were wasted. If the socket is lost during a poll, drop the `Poll` and send `Input::Lost`. A poll covers every profile in `instance.served`; a host's list call covers one profile, which is why there is one `Step::List` each.
6. **`Step::Snapshot` goes on a socket of its own.** New ticket, new socket, `session.resume`, read the reply, close the socket. Closing ends the subscription. Never keep it open and never send `end_reason`. The reply holds the session's whole history: allow 8 MiB frames. If it fails, call `poll.failed(&step)`: the model takes it again at the next poll. Give every `apply` the real time in milliseconds: the model spaces a session's snapshots 30 s apart by it. What a snapshot does to the session, and how often one comes, is under "How the cards follow Hermes".
7. **When to poll.** A timer that never stops: `gateway.poll_ms()` after each poll ends, which is 1 s (`BUSY_POLL_MS`) while any session starts, works or waits or a card shows, and 10 s (`IDLE_POLL_MS`) when everything looks idle. The slow poll is what finds a turn that no hook and no hint told of. Poll at once, as one "poll wanted" flag however many ask, on `Effect::Poll`, on a frame for which `hints(frame)` is true on any open socket (Hermes's `sessions.changed` and `platforms.changed`, which it sends at most every 2 s and can miss), when a Hermes hook reports a turn started, waiting or ended, at startup and after every reconnect. A wanted poll starts when the one under way ends. Hints and hooks only say when to poll. What waits is always read by the poll.
8. **Answer on a short socket.** Take the decision with `Requests::checked`, build `pending.reply(decision, scope)`. `Ok(None)` is leave it. For `Reply::Call`: new ticket, new socket, `session.resume` (an answer from a socket that is not subscribed is refused), send `call.frame(id)`, tell the model `Input::Sent`, give it the reply as `Input::Responded`, close the socket. For `Reply::Result` (a set of questions): resume, write the frame, `Input::Sent`, close. Nothing replies to it, so the model asks for a poll at once, closes the card when a poll no longer lists the set, and says `Effect::Unanswered` if it is still listed 5 s later.
9. **Effects to core.** `Open(p)` is `register_native(p.id(), p.view(now), now)`. `Changed(p)` is `refresh_native(p.id(), p.view(now))`, never a second request. `Close { id, session, .. }` is `settle_native(id)`; `session` is the full `SessionRef`, gateway included, and `session.hud_id()` is the HUD's session id. `Unanswered { pending, why }` gives the card back as it was (`Requests::put_back`, since ticket 27; it was `settle_native` then `register_native` again, which started its hold anew), plus a failed delivery; after `PermissionDenied`, resume and send again. `Marked(p)` and `Unmarked(p)` are `refresh_native` with the card as it is now (ticket 27). `Poll` sets the "poll wanted" flag. After any change call `set_native_waiting(AGENT.id, reader, &sessions, now)` with the sessions that have cards. After every input, effects or none, core is told `set_native_states(AGENT.id, reader, &gateway.live_states())`, since a poll can change what a session does without changing a card; when the observer stops, it is told an empty list and an empty `LiveStates` under the same reader. `reader` names who read (ticket 24): core keeps each reader's flags and states apart, each reading with its own `read_ms`, so one follower never replaces, renews or lapses what another told. A session follows the reading that lists it (the newer, if two do), and its hooks are compared with that reading's time. The other clients' channels pass `agents::SOLE_READER`. Hermes has a follower for each gateway (ticket 26), and each passes its own name, its gateway's id as written (`local`, `local/<anchor>`), the same for its whole life, and ends with `end_native_reader(AGENT.id, reader)`, once, which clears its states and flags and no one else's. Both go through 13's `tell()` (`platform/src/clients/hermes/effects.rs`), which runs after everything the model takes in and from `stop()`: ticket 16 added the call at its end (`clients::hermes::tests_unix::states`). Core changes nothing when told the very same reading again; any newer reading wakes the HUD, even of the same sessions, since it decides again against hooks that reported since the last one (at most once a second). `live_states()` carries `read_ms`, when the newest accepted poll came back; only an accepted poll moves it, so publishing after unrelated inputs renews nothing. Core stops believing a reading 30 s after `read_ms` (`LIVE_STATES_MS`, three idle polls) with no further call, so a poll that hangs gives the sessions back to the hooks without the connection noticing. There is no timer for deadlines: the model has none.
10. **Reconnect.** Socket closed or failed is `Input::Lost`. Back off, identify again every time, and do not expect the port to change after a restart. The model closes every card when the instance id changes. After a reconnect to the same instance, poll at once.
11. **Never.** Write under a Hermes home. Send `end_reason` on detach, which would close Nicky's session. Answer or show a `sudo` or `secret` request. Hold the collection gate while waiting on the network.

Still to measure in ticket 13: how long a whole poll takes against the one-second target (one list for each profile, two or more calls for each busy session, and the poll's own time adds to the age of what it found); how often real sessions need a snapshot, what one costs Hermes, and how large its reply is; how many calls the search for the oldest event takes on real streams; whether the poll's own list call makes Hermes publish a late `approval.settled`; and whether Hermes's `on_human_input_request` hook should be installed as the push for questions (today's hooks push approvals only). Unproven against a real gateway: the `profile` parameter on calls other than the two list calls (Hermes's dispatch routes every method by it, `gateway/session_controls.py:280`), a JSON list as an answer inside a set of questions (`tools/clarify_tool.py`, `_clean_answer`), Telegram sessions, a real old gateway, a draining one, and a stream past 512 events (the search for its oldest event is from source and a pretend gateway, not a recording).

### The connection, as built (ticket 13)

In `src/crates/platform/src/clients/hermes/`. `hooks::configure` starts it with the other native channels when client hooks are turned on and drops it when they are turned off, which withdraws its cards.

Where it differs from the list above:

- **Answers come through core's waiter, not `Requests::checked`.** `register_native` returns the place a card's decision arrives, as for the other native channels. Core puts the card away when it is answered. The connection sends the answer; if Hermes refuses it or says nothing, the card comes back under the same id with a failed or uncertain receipt (`Effect::Unanswered`), as the request it was, with the hold it had (ticket 27). A reply of `already_resolved` or `stale_generation` closes it with a failed receipt saying Hermes no longer waited.
- **Frames up to 64 MiB, not 8.** `session.resume` returns a session's whole history and answering needs it. At 8 MiB a long session could never be answered.
- **The timer.** The wait runs from when a poll began, not from when it ended. While the gateway lists any live session, a poll begins at least every 0.8 s (`Pace::watch`), whatever the model's timer says; for 5 s after a hint or a hook asked for a poll, too (`Pace::warm`). With the model's timer alone (10 s while every session is idle), a question asked just after a turn began showed 1.5 to 2.7 s late, and one answered elsewhere within 3 s never showed: Hermes's hints arrived 6 s apart and `sessions.changed` not at all. Hermes's desktop app asks the same list every 1.5 s. Two polls never begin less than 250 ms apart, and never run together.
- **A home its group may write is refused**, where Hermes looks up whether the group is the user's private one.
- **A socket for one answer or one snapshot that fails tells the model nothing.** Only the socket the polls run on says whether the gateway is there.
- **An answer is never written once the observer stopped or its card closed.** Sending one takes a ticket, a socket and a `session.resume`, and things change meanwhile: client hooks are turned off, the request settles elsewhere, the gateway restarts. Three things together make it hold (`visit.rs`, `wire.rs`). First, every visit is on the model's list of live visits from the moment its socket opens, with the request it answers. Second, everything a visit writes that matters (the first `session.resume`, the call for a question or an approval, the result frame for a set of questions, the second resume and the second try of a retry) goes through one path: under the model's lock the visit is checked to be still wanted (the observer runs; for an answer, the request still has its card and the gateway that is ready is the instance that asked) and marked as writing; the write itself runs with nothing locked. Third, stopping the observer, and closing a card, cut the socket of every visit they find writing (for a card, the visits that answer it) before they return: the stream is shut down, which ends a write that waits on the gateway at once, and nothing more is written through it. So either the check fails and nothing is written, or the write is cut and its frame never completes. A visit that is not writing is left to end tidily: it fails its next check, detaches and closes.
- **No write waits on the gateway under a lock, or for long.** One frame on a short socket has half a second to be out, all of it (`Pace::write`), however the gateway reads; on the socket the polls run on, five seconds. A write that fails or runs out of time cuts its socket: the WebSocket keeps what it could not send and would send it with the next frame, a detach or a close included, so nothing more is written there. Stopping does not wait for any of this: it marks, cuts and returns.
- **Written, not read: where the line is.** The promise is about writing. Nothing of an answer is written after the stop or the close, and a frame that was being written then never completes. A frame that was fully queued before the cutoff was sent in time, and the gateway may still read it afterwards: it can sit in the kernel while the gateway is busy, and a visit that is not writing is not cut. The coordinator ruled this in (2026-11-13). The part of a cut frame that the kernel already took still reaches the gateway too, followed by the end of the stream: a piece of a frame, never an answer. And tidying up is still written after a stop: the `session.detach` and the close of a visit that was not writing.
- **A receipt for every answer that got out, whichever comes first.** An answer is filed in the model in the very step that marks its visit as writing, under the lock and before its first byte (`out.rs`, `Out`). Three things can then happen in any order: the frame gets out, a poll closes the card, Hermes replies. Whichever closes the card finds the answer filed. A set of questions has no reply: its card closing after the frame is out is its receipt, and if the card closes while the frame is still going out, the receipt waits for the write to say whether it got out. A question or an approval whose card a poll closes before Hermes's reply gets its receipt from the reply. The reply is handled under one hold of the model's lock: it looks whether the card is already closed and, if not, gives the reply to the model, with no gap in between for a poll to close the card in. A frame that did not get out is forgotten, with no receipt.
- **A cut socket is shut down, not reset.** A reset (`SO_LINGER` 0) would also drop what the kernel still holds of the cut frame. It was tried and taken out: against a peer that had stopped reading, about one run in fifty left the peer never learning that the connection was gone, with no data, no end and no error for as long as it was watched (macOS, loopback). Hermes would have kept that subscription until its own keep-alive gave up. A shut-down stream always ended for the peer, in 100 runs of the same tests, and what it delivers first cannot complete a frame. The coordinator ruled this in on that evidence (2026-11-13), in place of the reset the design first called for. The residual it accepts: the bytes of a cut frame that the kernel had already taken may reach the gateway before the end of the stream, and a partial frame cannot complete.
- **Hints count on every socket.** A socket subscribed for an answer or a snapshot hears the session's events; each one for which `hints(frame)` is true asks for a poll, as on the socket the polls run on.
- **A gateway that cannot be reached is said once.** The state does not go back and forth with every dial. Dials wait 250 ms, then twice as long each time up to 5 s; a gateway without the live connection is asked again every 5 minutes.

Measured against Hermes 0.22.5 in a home of its own, a profile set to ask, a scripted model (ticket 13's Answer has the runs):

- From Hermes asking to the card, on the installed fork: 2 to 732 ms over 12 questions and 6 approvals, median about 230 ms. In a development build: 13 to 775 ms over 27, median about 400 ms. That is polling alone: no hook of that gateway reached the fork.
- One poll with nothing running: two calls (one list for each of two profiles). With a session working: four calls. On the installed fork 120 polls took 13 to 25 ms on average, the slowest 371 ms, and one of them took a snapshot.
- Killing the gateway while a question waits: the card stays until the gateway is back as another instance, then closes as `GatewayRestarted`, and the next question shows, with no relaunch. The same after a clean stop, where Hermes cancels the request as it goes: the card still stays the 15 s until the new instance is up, because a lost socket alone closes nothing.
- The `profile` parameter routes every call on a host's socket, not only the lists: questions in the default profile and in a named one were read and answered on the same socket.
- A set of questions answered with a result frame is taken: Hermes sent `request.cancel` with reason `resolved`.
- `on_human_input_request` is not installed as a hook. Polling meets the target without it, and each new handler is one more that Hermes asks the person to approve.

Not exercised against a real gateway: a stream past 512 events (the one snapshot above was of a short stream; how large a long session's snapshot is was not measured), a poll started by a hook (the test home's path is too long for the fork's hook socket, so that gateway's hooks could not reach it; `nudge()` is tested against the pretend gateway), Telegram sessions, a real old gateway, a draining one, a pointer file, Linux. Windows is not built: `control/windows.rs` is a stub.

To check against a real gateway, never use a Hermes home in use. Make a throwaway home with its own gateway (`HOME` and `HERMES_HOME` both redirected, as ticket 11 did), and run the hand-run test in `tests/live.rs`: `AGENT_HUD_HERMES_LAB=<home> cargo test -p agent-hud-platform --lib hermes::tests_unix::live -- --ignored --nocapture`.

### The route (ticket 25)

A refactor with no change in behavior, ahead of phase 2. Still one home, one gateway, one follower, the same threads and the same pace.

- **What the connection asks of a route** (`route.rs`): `homes()`, `exchange(home, line, timeout)` and `dial(instance)`, and a step that goes with each of the last two: `named(home)`, how the home is named once its gateway has answered, and `prepare(instance)`, what has to be in place for an accepted instance before a ticket is asked for. `link.rs`, `visit.rs`, `answer.rs`, `polls.rs` and `socket.rs` name no path, no unix socket and no address. A `Home` cannot be made or opened outside `route.rs` and the files under `route/`.
- **The route to this machine** (`route/local.rs`) told of one home, the root home, which is all phase 1 followed. Since ticket 26 it tells of the root home and of the home of every named profile under `profiles/`, each with the profile it is the home of. The home's links are resolved each time it is asked for, as before, so a home made or moved while the HUD runs is found.
- **The loopback check is the local route's**, and runs before it dials: an origin that resolves to no loopback address is `invalid_api_origin` and nothing is dialled. The model's own check in `identify()` still comes first, so such a gateway never gets as far as a ticket. `Socket::open` still refuses an origin that is not plain http before it asks for a stream, and still takes the `Host` it sends from the instance's origin.
- **The home is named again after its gateway answers**, as before the route. `identify`'s answer is held against the home as it is once the answer has come: `named` resolves the home's links once more, and a home that no longer leads anywhere goes by the name it was given. A home whose link was pointed elsewhere while its gateway was asked is refused as `ProfileNotServed` and never reaches a ticket. The first version of this ticket compared the answer with the home as it was before the question, called that a difference no run could show, and was wrong: the first PR review showed it with a link retargeted mid-question (`tests/verifier25.rs`).
- **The route is told of an accepted instance before its ticket is asked for** (`prepare`, called in `link::opened` ahead of every ticket). A ticket lasts 30 s, so whatever a route needs between a gateway being accepted and its dial (a forwarded port, for the route over SSH) is made there and kept. The route to this machine does nothing in it, so the order here is what it was: ticket, then the loopback check, then the dial.
- **Opening a socket stops when the observer does** (`opening.rs`). Opening waits in four places: the route preparing, the lookup of the ticket's home, the control socket's reply, and the dial. `prepare` is handed a stop signal (`Stop`, which the observer is), and a route that waits there waits on it too and ends what it began. Every one of the four waits is followed by a look at stop, and once the observer has stopped nothing further is asked of the gateway and nothing is dialled. The stream itself is on the model's list of sockets from the moment it arrives until it is open, put there in the same locked step that looks at stop, so stopping cuts a stream that is being upgraded, and one that arrives after the stop is closed with nothing said on it. The model is locked to list the stream and to take it off, never across the route or the socket.
  - **What is not promised.** A step that looked at stop a moment before the observer stopped still begins: one exchange with the control socket, or one dial, can start in that instant. What it brings is dropped: the stream is closed with nothing said on it, and the ticket is never used. Closing that too would mean stopping has to wait for the route, and stopping never waits.
  - **A dropped ticket is not without effect at Hermes** (accepted by the coordinator after the fourth PR review, 2026-11-13, as a bounded residual). "Dropped" means the ticket expires unused within the 30 s a ticket lasts. Until then Hermes counts a client as attaching, and an auto-started gateway's idle watcher will not exit, or restart for a pending change, while it does. So turning hooks off at the very moment a socket is being opened can hold such a gateway up for at most 30 s. It takes a stop that races an opening, it cannot last longer than the ticket, and no session is touched.
  - **A Close frame can follow a stop** (accepted the same way). A socket whose upgrade finished just as the observer stopped has left the list before its caller gets it. The caller sees the observer has stopped and closes the socket, which writes a WebSocket Close frame after the stop. No answer and no `session.resume` is sent. Ticket 13 already lets an established visit that is not writing detach and close after a stop; this is the same tidying up.
  - **Ticket 13 had the same opening with no look at stop at all**: an opening under way when hooks were turned off, at any point of it and not only in that one instant, asked for its ticket, dialled and upgraded, and then closed unused. Its ticket was used, so Hermes saw a client attach and leave where it now may see one attaching for up to 30 s. Nothing was written on such a socket then, and nothing is now; what changed is that it is no longer begun, or is cut. The second and third PR reviews found the first two versions of this incomplete: first `prepare` could not be stopped, then the two waits after it had no look (`tests/reverify25.rs`, `tests/reverify3.rs`).
- **Tests.** `tests/route.rs` holds the route the tests follow (`Way`): the lab's home, reached as the local route reaches a real one, with every call kept and a switch that shuts it. `tests/reverify3.rs` holds the third review's two: an opening held at the ticket's home lookup, and one held at the ticket's reply, until the observer has stopped. `tests/reverify25.rs` holds the second review's three: a route that makes a real forward in `prepare` and dials through it, one whose preparation fails, and one still preparing when the observer stops. `tests/verifier25.rs` holds the first PR review's two probes: a home whose link changes while its gateway is asked, and the order a recording route is asked in (told of the instance, then the ticket, then the stream). `tests/script.rs` is one scripted run whose log is compared line for line; it was written and run on ticket 13's code first (60 runs of 60), and gives the same log after (60 of 60).

### Gateways and followers (ticket 26)

New behavior on this Mac, on top of the route: several gateways, one follower each.

- **Finding them** (`discovery.rs`). The route tells of the root home and of each folder under `profiles/` that Hermes would name a profile by. Each is asked `identify`, with nothing locked. A home counts only when its control socket answered as a ready gateway that serves that very home. The answers are put together by `instance_id`: each instance is one gateway, and it serves the profiles its own answer lists. A home that did not answer says nothing, neither that its gateway is gone nor that its profile is free.
- **When.** At start, every 10 s (`Pace::discover`), and at once when a follower asks: its socket was lost, a call was refused as `profile_mismatch`, its home answered as another instance, or its gateway serves other profiles than before. Looks are at least 250 ms apart.
- **Followers** (`followers.rs`, `follower.rs`). The gateway that serves the root home has a follower from the start, named `local`, as in phase 1: it goes on asking where no gateway is there. Every other gateway gets a follower when a look finds it, named by its anchor profile (`local/<anchor>`), made from the answer the look got, so it starts ready. A follower asks the home of its anchor, polls only the profiles its gateway serves, and tells core under its id as reader name. Its lines in the log begin with its id; the lines of `local` are as they were.
- **The first poll waits for the first look**, so a profile two gateways claim is known as that before either opens a card for it. A look takes milliseconds on this Mac, and up to the control socket's 5 s for each home whose socket is there and does not answer.
- **What ends a follower** (`settle.rs`). Client hooks turn off. Or its home answers as another instance and its own instance was heard nowhere: the follower finds that itself when it next identifies, says so, and the look that follows ends it, closes its cards as `GatewayRestarted`, and makes a follower for the gateway that answers now, its anchor picked again. Or every profile it held is another instance's. A missing socket, a stopped gateway and a look that timed out end nothing: the follower keeps its cards and keeps trying.
- **A name is never taken from a living follower, and no gateway waits for one.** A follower keeps its id after its anchor profile left its gateway. If another gateway then serves that profile and would be named the same, the newcomer is told apart by its instance and followed at once: `GatewayId::apart`, written `local/<anchor>~<8 hex>`, the hex being the first four bytes of the SHA-256 of the newcomer's `instance_id`. Two instances can hash to the same four bytes, so where that name is taken too, the newcomer takes the first free one of `local/<anchor>~<8 hex>~2`, `~3` and so on (`GatewayId::apart_again`), in that same look: no gateway that was found is ever left without a follower for its name. A profile's name holds no `~`, so none of these is an anchor or another gateway's id; a name is the same for as long as its follower lives; and a restart picks the name again, the plain one if it is free by then. The living follower, its request ids, its cards' creation times, hold deadlines and dismissals are untouched. The first version ended the living follower and made it again under another name; the second made the newcomer wait for the name, with its questions hidden for as long as the old gateway ran. Both PR reviews caught those.
- **A profile that leaves a running gateway.** Its own verified answer no longer lists the profile, or a verified answer shows another instance serving it while its own was not heard: the model takes `Input::Retired`, that profile's cards close as `Retired`, and the follower keeps its id for the rest. If the profile was its anchor, the follower asks another of its homes from then on. A new follower for the gateway that serves the profile now, or the growth of an existing one, comes in the same look, after the close.
- **Two gateways claiming one profile.** Both are polled for it and neither opens a card (`Input::Withheld`); cards that already show are kept and close as Hermes says. The claims are what each instance that answered says it serves, and what each follower whose instance did not answer still holds. When a look hears every claimant and one alone still claims the profile, a poll is asked for at once and opens what waits.
- **A gateway that was not heard keeps its claims.** Only a verified answer of that same instance takes a profile from a follower. A missing control socket is not that: the gateway behind it may run and be polled on the socket that is open. So a look that did not hear a follower's instance takes nothing from it, counts what it holds as claimed, and ends no contest there was. The same holds for a look that missed a reply (`Seen::missed`): a control socket that did not answer in time or answered what cannot be read, or a gateway that is still starting. Something is there and may claim. A home where no gateway can be asked misses nothing by itself: nobody listens there, the way to its socket is closed to this user, or what is there is not the user's own. Such a home answers the same at every look, so counting it as missing would keep every contest on the machine for ever (one folder with no gateway that cannot be entered did, until the fourth PR review). A gateway that was followed there keeps its claims all the same, by its follower. The one thing that ends an unheard follower is its home answering as another instance, which it finds for itself (a restart).
- **A gateway that is gone claims nothing** (`Shared::gone`, set in `asking.rs` where the follower asks who is there). Gone is the follower's own finding: it has no socket open on its gateway, and when it last asked, either nobody listened at the control socket of its home, or every home of the machine was read and its home was not among them (the profile's folder was removed). Only a home list that was read whole says that (`Route::inventory`, `Inventory::whole`): where `profiles` cannot be opened, an entry of it cannot be read, or a folder in it cannot be resolved though it is there, the list is not whole, what is missing from it is not known to be gone, and the mark stays as it was. The root home is told all the same, so this machine's own gateway is followed as ever. The mark changes only with what an asking found. Such a follower is no claimant, and no claimant left to hear, so a contest it was part of ends at the next whole look and the gateway that still serves the profile opens its cards. Nobody has to turn client hooks off and on. The follower itself stays, as every follower of a stopped gateway does: it keeps its cards and its profiles and goes on asking, and if a gateway comes back at its home as another instance, that is a restart. Not gone, and so still claiming: a gateway whose follower's socket is open, whatever became of its control socket; one whose control socket is there and does not answer in time (a stall); one whose control socket cannot be asked or fails in a way that does not tell (below); and one on a machine whose homes cannot be told just now, or not all of them. A route to a far machine must not report a lost link as nobody listening (ticket 30).
- **What says that nobody listens** (`route/local/unix.rs`, `nobody`). Only two errors: nothing is there (`ENOENT`, and a link in place of the pointer file, which is not read, as ticket 13 has it), and nobody takes the connection (`ECONNREFUSED`). Those are `Silent::Absent`. A permission error, and any failure once the connection was taken (a reset, a broken pipe), are `Silent::Unclear`: something may run there, and a follower that met it is not gone. Before this, every failed connect and every failed read or write was `Absent`. A control socket is asked only where its owner may read and write it (mode `0600` or `0700`): one of mode `000` was "private" to the check ticket 13 made and is refused now as not the user's own to use.
- **A residual, accepted: a gateway that hangs for about seven minutes can be taken for gone.** On macOS a Unix socket whose listener is alive and does not accept refuses the next connection (`ECONNREFUSED`) once its queue is full; it does not make the caller wait. Hermes opens its control socket with a queue of 100 (`gateway/control_socket.py`, asyncio's default). Every identify that timed out stays in that queue until the gateway accepts again. So the case is exactly this: a gateway hangs without closing its control socket, its follower has lost its WebSocket to it, and about 100 identifies go unanswered, which at the app's pace (a look every 10 s, a follower asking twice in 15 s) takes about 7 minutes. From then on the control socket answers as if nobody listened, the follower takes its gateway for gone, and a profile it contested is released to the other gateway. A hung gateway usually keeps its WebSocket open, and then its follower never asks and nothing is released. There is no cheap way to tell a full queue from a socket nobody listens on. The fourth PR review found it and the coordinator accepted it as it is (`evidence/26/verifier-files-4/backlog.py` and the probe `round4_a_live_listener_with_a_full_queue_is_not_word_that_nobody_listens`, which is not tracked: it fails by design).
- **A follower back from gone waits for a look.** While its gateway was gone its claims were dropped, and a contest may have ended on that. When it hears its gateway again it claims again, so its first poll waits until a look that began after its return is settled (`Shared::awaits`, the looks numbered in `signal.rs`). It asks for that look at once, whether or not the profiles it serves changed. So no card of a profile that is contested again opens in between. The wait ends with any look that is settled, whole or not: an unheard follower that is not gone counts as a claimant, so its claims are back in either. A look that could not be taken at all (the homes cannot be told) ends no wait.
- **No retry once it ended.** An identify that only was slow is asked once more, by a follower that still follows. One that ended while the first try waited asks nothing more (`link.rs`, `asked`). Phase 1 retried without looking; the third PR review found it.
- **One name for a profile.** A served home's profile is its path alone (`Profile::of_home`), for ids and for the `profile` of every call. A home's place in the configured root (`Home::profile`: the root, or `profiles/<name>`) says which home a follower asks and what the gateway's anchor is, and names no session. The two differ only for a root configured at `…/profiles/<name>`.
- **A follower that ended polls no more** (`polls.rs`). The stop is looked at before each round of a poll and before each call of a round, so a reply that was held when the follower ended comes back to no further call. Phase 1 had this gap; the first PR review found it.
- **Ending is one step, once** (`Shared::end`). What the follower was writing is cut, its cards close or are withdrawn, and core is told its reader has ended, all before the set's lock is let go, so before any follower that takes its place is made. A second end does nothing, whenever it comes. An answer that was written before a follower ended with its gateway still gets the receipt Hermes's reply gives it, as when one follower lived through a restart; one cut by hooks turning off gets none, as before.
- **Ticket 25's stop rules hold for every follower and for the look.** Each follower opens sockets through `opening.rs` with its own stop. The look asks `identify` only, never a ticket, and takes no step once the observer stopped. The residuals are the same and now apply to each follower: one control exchange or one dial that began in the instant of a stop, whose ticket expires unused within 30 s, and a Close frame on a socket whose upgrade had just ended. A look adds one of its own kind: an `identify` that began in that instant is answered and dropped, which costs Hermes nothing.
- **Locks.** The set of followers is locked to make and to end one, never across a wait on the network. The order is set, then one follower's model. No thread of a follower takes the set's lock.
- **Not covered.** A profile folder that is a link to a place outside the root is not followed by a gateway of its own (its home is no profile of the root). A profile a gateway starts to serve between two looks can get a card in the moment before the look it asks for. Cards of a profile whose folder was deleted stay until the HUD's own hold ends them, like any card that is out of reach (ticket 27 marks those).
- **Tests.** `tests/gateways.rs`: both layouts, the same ids whichever home is asked first, a look that times out on one home, a profile created while it runs, stopping and restarting one gateway, moving a profile, a contested profile, and a contest that ends when one claimant is truly stopped (no hooks toggled) or comes back without the profile. `tests/followers.rs`: a follower stalled past 30 s, a completion hook followed by the other follower's poll (through a real core), `the_anchor_profile_is_retired_from_a_running_gateway`, `a_late_end_does_not_clear_the_replacement`, `a_reader_ends_once`, receipts and stop. `tests/verifier26.rs`: the first review's five probes. `tests/reverify26.rs`: the second review's two, and its real-gateway routing run against the pretend gateway, which names a profile as Hermes does (`hermes_name`). `tests/round4.rs`: the fourth review's six (an unreadable `profiles` folder, a folder with no gateway that cannot be entered, and its four controls), and the home list itself. `tests/round3.rs`: the third review's seven (two newcomers told apart alike, a removed home, a socket its owner may not use, the same instance back from gone, a retry after the stop, and its two controls), and what each fix rests on. `core/src/tests/hermes_identity.rs`: one row for a profile-shaped root. `agents/.../tests/served.rs`: the model's three new inputs, the name of a home in a `profiles` folder, and the name of a gateway told apart. The pretend gateway can serve chosen profiles with a control socket in each home and refuses a call for any other as `profile_mismatch` (`Fake::serving`). Tests that pin what one follower asks of its route run with no look by the clock (`Pace::discover: None`).

### Cards out of reach (ticket 27)

A card is never withdrawn because its gateway is out of reach. Hermes may still be waiting. The card stays, says so, takes no answer while it does, and is reconciled when the connection returns. This holds for every route, this Mac included, and **it changes phase 1**: the card of a stopped local gateway used to look answerable and fail on the click.

- **No timer is added and none is removed.** The HUD's own hold (ten minutes by default) ends a marked card at its deadline exactly as it ends any other: the card goes, nothing is sent, and it counts as dismissed, so it does not come back when the gateway does. Hermes's own timeout and settlement are seen at the first poll after the connection returns. Reconnecting never stops for being out of reach for long.
- **The mark** is one optional, client-neutral field of a request view, `unreachable`: the reason as text, made with the Hermes adapter in both languages (`agents/src/hermes/gateway/card.rs`, `out_of_reach`, `Pending::view_out_of_reach`). A card that can be answered does not have the field. Core carries it and decides one thing from it, the gate below.
- **When a card is marked** (`agents/src/hermes/gateway/reach.rs`). When the socket to its gateway is lost (`Input::Lost`, which is also every failed dial), and when an answer to it could not be sent (`Input::Unsent`). The model says `Effect::Marked` once for each card, and the connection changes the card in place with `refresh_native`. It is never registered again: no second request, no second `needs-you`, and its creation time, hold deadline and dismissed state, which are core's, are not touched. A card that was dismissed before the outage stays dismissed through it. The log says `unreachable id=<request>`.
- **When the mark goes.** When a poll that counted read the card's session whole and found the request waiting (`reconcile.rs`, `Effect::Unmarked`, the log's `reached id=<request>`). The first poll after a reconnect does that for every request that still waits, with no sound, and closes the ones that are over as the model says (`Settled`, `TimedOut`, and so on), with no note of a failed delivery, since nothing was answered here. A poll that could not tell (its profile's list failed, or its session's read did) leaves the mark until one can. A gateway that is ready again and not yet read leaves it too.
- **The gate is core's `Requests::answer`** (`core/src/requests/answer.rs`, `reachable`), and `checked` with it. A decision for a request whose view has `unreachable` is refused with that reason, before anything changes: the card is not removed and not dismissed, its hold is where it was, and its adapter hears nothing. Before this, `answer` removed and dismissed a native card before the adapter saw the decision. **Leaving the card alone is still taken** (`kind: "leave"`, the card's dismiss): it sends nothing anywhere, and ticket 38 needs a marked card to be dismissable.
- **The adapter holds the same rule** (`platform/.../hermes/follower.rs`, `instance_of` and `Model::current`). Before it opens a socket for an answer it asks whether the request's card is marked and its gateway ready, and every frame of an answer is checked against the same under the model's lock before it is written. If not, nothing is sent.
- **The mark ends every answer that was not sent** (`platform/.../hermes/out.rs`, `lost`; the first and second reviews of ticket 27). When a card is marked, an answer being written to it is cut through ticket 13's socket cancellation, as when a card closes: a write that was let through and has not begun never begins, and one under way never completes; the write itself still runs with nothing locked, and a frame that was fully queued before the cutoff may still be read, as ticket 13 ruled. Then core is told of the mark, and every decision core took for the card before it is over. One the answers' thread holds, or that waits to be picked up, is given back at once: the request waits again as it was, marked. So an old decision is never sent after a reconnect. Once a poll finds the request waiting, the card is answerable again with the hold it always had, and it takes a new click; the decision from before the loss opens no socket and writes nothing (`answering`, and the look at `Model::taken` before every frame). Its receipt says the answer failed, or that it is uncertain where its frame had been let through.
- **What makes a decision stale cannot be raced** (`core/src/requests/back.rs`, `mark_native`, `current`; `platform/.../hermes/decisions.rs`). Core takes a decision under its lock and hands it to the adapter after letting go of it, so a mark can land between the two, and nothing the adapter can look at then shows that a decision is on its way. So core counts. Every request counts how often it was marked as out of reach. `answer` records that count with the decision, in the one locked step that takes the card away. `mark_native` counts on, in a locked step of its own, whether the request still shows or its decision is already taken. A decision is current only while the two counts are equal (`Requests::current`). The adapter asks when a decision reaches it, however late, and one that is not current is never sent: its card is given back as it was for a new answer, with a failed receipt. A decision taken after the mark is gone again, or after the card was given back, is taken at the newer count and goes through. Looking into the channel at the mark only brings a card back sooner; it decides nothing.
- **One record for one answer** (`out.rs`, `Out::taken`; `answer.rs`). What an answer files for its receipt is keyed by the request, and a card that came back can be answered again while the thread of the answer before is still returning from a write that was cut. Each record names the wait its decision was taken in, and every step of an answer's thread (a write that failed, one that got out, Hermes's reply) changes or removes only its own. A reply to an answer that is no longer the one that is out says nothing of the one that is: a poll tells what became of the request. The mark looks the same way when it says what became of the answer it ends: uncertain only where that answer's own record is filed, failed where it never got as far as a write, whatever the answer before it left filed. And one decision has one receipt: an answer that could not be sent is said to have failed by the mark that gives it back, and not a second time by the thread that found it could not be sent (the third review of ticket 27).
- **One receipt for every answer core took** (the fourth review of ticket 27). However an answer ends, core is told once what became of it: confirmed, failed or uncertain. The ends that had none before: a request that settles, or a follower that ends with its gateway, after core took the decision and before anything of the answer was written (failed, from the close: `effects.rs`, `Effect::Close`, and `out.rs`, `closed`, which knows the wait of the decision that was out and counts as filed only that decision's own record); a decision that still waited to be picked up when its card closed (failed, the same way); an answer cut by its card closing while its frame was going out (failed, from the thread whose write was cut; ticket 13 said nothing of it); a poll that closes the card after the answer was written, and a reply that then refuses it or never comes (failed, or uncertain, as with the card still showing: `effects.rs`, `unlanded`); and a set of questions that ends another way than settled after its answer was written (uncertain). **Turning client hooks off stays the one end with no receipt**, as ticket 13 has it: the cards are withdrawn without a word. And the stop is no lost connection: a follower says it is ending before it takes its model, and a thread that sees that in between brings no loss to the model (`follower.rs`, `apply`; `link.rs`), which used to mark the card and say an answer that was out had failed.
- **A close asks core what it took, not the channel** (`core/src/requests/back.rs`, `close_native`, `hand_over`; the fifth review of ticket 27). Core takes a decision under its lock and hands it over after letting go of it, so a card can close in between, and a look into the waiter's channel then finds nothing though a decision is on its way. So the close does not look. `close_native` ends the request in core, as settling does, and in the same locked step takes back the decision on record for it and returns the wait it was taken in; the follower gives that decision its one receipt, failed. A decision core took back before handing it over is never handed over: `hand_over` looks and sends in one locked step, so it cannot happen after, and `answer` still returns `Ok`, since the click was taken and has its receipt. Turning hooks off settles as before and takes nothing back.
- **An answer that loses the race.** Core took the decision and put the card away, and the connection went before the adapter sent it. The adapter sends nothing and gives the request back: `Requests::put_back(id, wait, view, now)` (`core/src/requests/back.rs`). The request waits again under the same id, with the time it first came and the hold that runs from it, not dismissed, where it stood among the others, and marked. It is not `settle_native` then `register_native`, which would start its hold anew. No sound: an alert is decided by request id, and this is the same request. The receipt says the answer failed. Phase 1's `undelivered` and `Effect::Unanswered` both go this way now, so a card whose answer Hermes refused or did not confirm also keeps the hold it had.
- **A put-back never reverses a later decision.** Every wait of a request has a number (`Ticket.wait`: one for each registration and each put-back), and core keeps, for each native request it took a decision for, the wait that decision was taken in (`taken`). `put_back` restores only that wait. It restores nothing where the hold ran out meanwhile (`expire` drops what was taken with it), the source settled or cancelled the request (`settle_native`, `cancel`), everything was cleared, the request was put back already, or a later decision was taken in a later wait. The adapter keeps the same number for the answer that is out (`Model::taken`): an answer whose card came back since writes nothing more, and a refusal that arrives late for it is dropped.
- **The session keeps showing as waiting** while its card is there: the follower's waiting flags have no time of their own. Its other live state goes with its reading, at once when the socket is lost and after 30 s where a poll hangs.
- **What it does not do.** A gateway whose socket is open and that answers no poll is not marked: a poll that could not tell leaves the cards as they were, as before, and the first answer that cannot be sent marks its card. Drawing the mark and turning the answer buttons off is ticket 38; until then the gate is what protects a marked card, and a click on one shows the refusal.

## The SSH link (ticket 28)

`src/crates/platform/src/ssh_link.rs` and the folder beside it. Spec section 6 is the design; this is what was built and what a caller must know.

| File | Holds |
| --- | --- |

| `target.rs` | `Target`: host, user, port and key path, made only by `Target::new`, which refuses a host or user outside letters, digits, `.`, `-` and `_`, or with a dash in front, or longer than 255. | `unix/process.rs`, `unix/words.rs` | One process waited for against a deadline without blocking on a pipe; the far command line; what the master's last words mean. |

The ones that start processes are marked `#[ignore]` and run by `the_lab_tests_pass`, in a process of their own. |

What a caller must know:

- **Call `Folder::sweep` once at launch, before the first `Link::open`.** It closes every master in the folder, whoever started it. Called later it would close this launch's own links.
- **The folder's path is at most 77 bytes**, so that a socket's path is at most 86: a socket address holds 104 bytes with its end and `ssh` adds 17 while it binds (measured: a master binds at 86 and refuses 87). On this Mac `~/Library/Application Support/com.nickymolina.agenthud/ssh` is 75 bytes, which leaves two to spare, and `~/Library/Caches/com.nickymolina.agenthud/ssh`, beside the instance lock, is 62. Ticket 30 picks the folder; the caches one leaves room for a longer user name. A folder that is too long is refused as "control folder path too long for a socket", and no machine is reached over SSH until it is shorter.
- **`End::CutOff` does not mean the far program stopped.** A test shows one that ignores the closed channel finishing 4 s after an 0.8 s limit cut it off. Run only far programs that carry their own deadline, and count a cut-off one as running until then. A `Failure::Lost` from `run` means the same.
- **`End::Ended(255)`** is a far program's own status only while the link is alive; `run` checks, and returns `Lost` otherwise.
- **A forward request is refused unless it leads to `127.0.0.1`** with a port. The local end is a free port on `127.0.0.1` that the link picks.
- **A command line is at most 4096 bytes and holds no `<<`.** A long program goes in `stdin`, with a script such as `exec python3 - "$@"`.
- **Clients never dial.** A command or a forward is a second `ssh` that speaks to the master's socket. It reads no configuration file, and is given a host name no network resolves, a proxy that fails, no key, no agent and an empty host list. So with the master gone, nothing reconnects by itself, and a client never opens the user's keys or `known_hosts` (without those last settings `ssh` reads the default key files before it finds the proxy dead).
- **A forward request must not carry `ClearAllForwardings`:** `ssh` then drops the very forward asked for and reports success (measured). The master carries it; forward and cancel requests do not, and read no configuration file instead.
- **`alive()` empties the master's log once it passes 256 KB.** Call it now and then on a link that stays up.
- **A key path is given as `-o IdentityFile="…"`, never with `-i`.** `ssh` looks for a file named by `-i` exactly as written, and reads `%` tokens in the same text afterwards, so a path that holds `%` survives neither spelling: doubled, the file is not found and `ssh` drops the key with a warning; plain, the tokens are replaced. As an option's value the path is quoted (`"` and `\` escaped) and `%` is doubled, and files named with `%`, spaces, quotes, `#`, `$` and backticks each sign in with every other identity turned off (`trust::v_percent_key_is_the_selected_identity` and its neighbour).
- **Cleanup removes a socket only once its master is confirmed gone.** A socket's master is every process that could be it: the one its record names, the one that answers on it, and each whose arguments name it in the process list. So a master with no record that does not answer (stopped, or hung) is still found, ended and confirmed gone before its socket goes. Where the process list cannot be read, the socket stays (`cleanup::v_cleanup_must_not_unlink_a_live_unresponsive_master_without_record`).
- **A lab login is a login to the real account, so the lab turns off what it would read of the user's.** `PermitUserRC no` and `PermitUserEnvironment no` (no `~/.ssh/rc`, no `~/.ssh/environment`), the lab's `authorized_keys` only, no host-based sign-in and no X11. `sshd` runs each command with the account's login shell, which reads the user's startup file (`~/.zshenv` for zsh): the lab's `sshd` sets `ZDOTDIR` and `XDG_CONFIG_HOME` to a folder of its own, and `BASH_ENV` and `ENV` to nothing, so the shell reads the lab's file instead. What a lab login still reads: the system's own files, and whatever the far command opens. Held by `isolation::v_lab_disables_user_ssh_startup_files` (reads `sshd -T`) and `isolation::a_lab_login_reads_the_labs_shell_startup_file_and_not_the_users`. `tests/lab.rs` has the list.
- **Lab tests run in a process of their own.** Starting a process shares this process's open files with it for a moment, a held file lock among them. The instance lock's tests (upstream's) let a lock go and take it again at once, and then find it still held: beside one existing test that starts a single process (`os::unix::pids`) they failed in 9 runs of 15 on a busy machine, with none of this code involved. A lab test starts hundreds of processes, so in the same test program they failed in 14 of 15. A later ticket's lab tests should be marked `#[ignore]` too and started with `lab::in_a_process_of_their_own("<their module path>::")` from one test that is not. To run the link's here and see what each prints: `cargo test -p agent-hud-platform --lib ssh_link::unix::tests -- --ignored --nocapture`.
- **Not verified here:** Linux (the same code, never run), an `ssh` older than 8.7 (it does not know `ForkAfterAuthentication`), a far login shell other than zsh, a host reached through the user's own `ProxyCommand`, and the user's real `~/.ssh/config`, which no test reads.

## The far history reader (ticket 36)

Spec sections 7 and 14 are the design; this is what was built and what ticket 37 must know. Nothing schedules a read yet.

| File | Holds |
| --- | --- |
| `agents/src/hermes/far_history/reader.py` | The program that runs on the far machine. 299 lines, standard library only. |
| `agents/src/hermes/far_history.rs` | `Request` (probe, fingerprints, rowids, sessions, held), the program's arguments, the column lists, `fingerprint_sql` and `local_prints` (the same fingerprint from a database on this Mac). |
| `agents/src/hermes/far_history/reply.rs`, `rows.rs` | `parse`: an answer checked whole. `Reply`, `Session`, `Cell`, `Prints`, `Rejected`. |
| `platform/src/clients/hermes/far_history.rs`, `failure.rs` | `Reader::read`: one read over a `Link`, with the checks on its exit status, standard error and answer, and what it does to the slot. `Settings`, `Failure`. |
| `platform/src/clients/hermes/far_history/batches.rs` | `Reader::prints`, `sessions` and `held`: the three reads as calls. Halves a read that is too large and skips a session that cannot be read whole. |
| `platform/src/clients/hermes/far_history/slot.rs` | `Slots` and `Slot`: one reader at a time for each machine key. |
| `platform/src/clients/hermes/far_history/unix/tests/` | The lab tests: ticket 28's throwaway `sshd`, and a `state.db` made from Hermes's own schema (`schema.rs`) with made-up rows. |

What a caller must know:

- **Keep one `Slots` for the whole app and ask it for a machine's slot by its key** (`Slots::of`). Never make a slot for a link, a route or a refresh. Call `Slots::retired` when a machine is retired. A slot starts as "held, start unknown", so the first read of every machine after launch runs a probe first, which costs one more round trip.
- **`Reader::read` blocks.** It waits for a read under way on the same machine, and for a reader that was cut off after it started (at most the deadline and the margin, 22 s). Call it from a thread that may wait. It never waits on a slot that is held with its start unknown: it probes, and returns `Failure::Busy` if a reader is alive there.
- **`Failure::Busy` means ask again later.** It is what a probe returns while another reader of the same home is alive on the far side, whoever started it.
- **An answer is used whole or not at all.** `Reader::sessions` returns the sessions that came whole, the ones skipped with why (`Skip::UsageRows`: more than 500 usage rows; `Skip::TooLarge`: one session over the output bound; `Skip::Id`), the ones not in the far database, and, where a read failed, why and which ids were never asked for. A session comes with every one of its usage rows or is not in `read`.
- **The home given must be the far home's canonical path.** The program checks it against its own `realpath` and refuses otherwise, so one home has one name in the far process list however it was reached.
- **One reader for a machine on the far side too, whichever home is read.** Every reader carries one argument, its mark: `agent-hud-far-history:`, the machine's key, a colon, and sixteen hex characters that name the home. A reader that finds another process of the same user whose mark has the same machine key, or names the same home, opens nothing and answers "busy". The key is the slot's (`Slot::machine`), so a probe for one profile finds a reader of another profile of that machine. This is what the first review found missing: after a relaunch or a retired machine the slot knows nothing, and its probe asked only about the home being read (`evidence/36/verifier-report.md`, finding 1). The key and not the far user as a whole, so that two far installs under one login, and two labs on one Mac, do not hold each other up.
- **The fingerprint** is `ended_at`, `last_activity_at`, then the counts exactly as `session_counts.rs` takes them, as one text. Store what a sessions read carries (`Session::print`) and compare it with the next fingerprint page. `local_prints` gives the same text from a local database.
- **`Cell` is a far value as SQLite held it** (none, whole number, real, text; a blob comes as none). `rusqlite::types::Value::from(&cell)` writes it back as it was, in the order of `SESSION_COLUMNS` and `USAGE_COLUMNS`.
- **A reader that waits for another to leave answers "busy", whatever its deadline.** Two readers that start together settle it by process id: the higher one answers "busy" at once, and the lower one waits for it to leave. An older reader can have the higher id too, once the system's ids have gone round, and then the newer one waits for a reader that stays: three seconds, then "busy". Before, the time a reader had to start in was its deadline, so with a deadline under three seconds its watchdog ended it first, with status 3 and no answer. No two readers ever had a database open over this (found by a run of the lab tests in which the ids went round).
- **The far reader's deadline counts from its `started` line.** Before that it only reads the process list, and a watchdog covers that too: the reader has its deadline to start in, and never less than twenty seconds, which is the deadline it has outside the lab. On a busy machine starting takes seconds: with this Mac at five times its cores, Python took four to start and one listing of the processes took ten. At the deadline the process exits with status 3 whatever it is doing; a system timer stands behind the watchdog one second later.
- **No value over 64 KiB is loaded on the far side.** The output bound alone did not bound memory: the reader built each whole row and its JSON before it looked at the bound, so a 64 MiB title made it hold about 270 MB (first review, finding 2). Now every value's length in bytes is asked in the SQL first, with `octet_length`, which SQLite answers from the row's header without loading the value, and a value over 64 KiB is never selected. A text that begins with a NUL, and one of many-byte characters, are measured by their bytes like any other. A session that holds such a value is too large: the read answers "too large", the caller halves down to it and skips it whole as `Skip::TooLarge`. On a page of fingerprints, a session whose fingerprint would be made of such a value has the fingerprint `oversized`, which is no session's own, so it is fetched once and skipped. A reader like this holds at most about 31 MiB over its whole life here (22 at rest; the rest is SQLite's page cache as it walks past the value), and the test holds it under 40.
- **A far SQLite older than 3.43 is refused.** It has no `octet_length`, and `length` is no stand-in: it loads a text to count it, stops at a NUL, and counts characters, not bytes (second review, finding 2). The reader says `sqlite-old` before it starts and opens nothing, and the caller reports `Failure::Refused(No::SqliteOld)`, "the far SQLite is older than 3.43, which cannot bound what it reads". Such a machine has no history in the HUD.
- **The reader also watches its own memory, and that is a watch, not a bound.** For a column declared REAL (the stamps: `started_at`, `ended_at`, `last_activity_at`, `first_seen`, `last_seen`) SQLite loads a value even to say how long it is or what type it has (measured, and the second review's opcode trace shows why: the load is followed by a conversion, so the header-only reading is lost). Neither the system nor this SQLite offers a memory limit a Python 3.9 can set. So the watchdog thread looks at the process's memory every half millisecond and ends it, with status 5, once it has grown 12 MiB and twice the output bound past what it was at `started`: about 36.6 MiB here. The process is ended at the next look, so its memory passes that mark by what arrives until then. Measured over 110 readers on a quiet Mac, each over its whole life as the system counted it: 39.7 MiB at most, with a 256 MiB text in a stamp column. The second review measured 46 MiB with the watch at 2 ms. The test holds these readers under 64 MiB, which leaves room for a look that comes a few ms late; it is not a promise. The caller takes status 5 on a read of rows as "too large".
- **A row that cannot be read does not stop a sweep.** A page of fingerprints that holds such a row is asked again in halves. When the page is that one row, `Reader::prints` asks for the rowids alone of that page (`Request::Rowids`), a read that loads nothing of a row. That read and the one that failed are two far processes, and a writer may have removed the row in between, so the row named now can be the healthy one after it. So the named row is read once more, by itself. If it reads, it is a fingerprint like any other. Only if it cannot be read either does `Reader::prints` return a page with no fingerprint, the row's rowid in `Prints::skipped`, and `last` set to it, so the next page starts after it. One row, one more read: nothing goes round again. What is left, and passes over no row that exists: a rowid that is gone can be logged as skipped, where the named row is deleted after its own read failed, or is deleted before its own read and the row after it cannot be read either. The log says `history prints quarantines rowid N: too large to read, and stepped over`, and nothing else of the row. Keep `skipped` if the row should be shown as not readable. Sessions on either side are read. A read of that session by id still refuses the whole session (second review, finding 1; third review, finding 1).
- **A table that declares a column named `rowid`, `_rowid_` or `oid` is not read at all, a generated column included.** SQLite reads such a column in place of a row's own number, whatever its case and whether it is plain or generated, so a database with one could choose the "rowid" that is skipped and logged, could make a table of healthy sessions read as empty, and could make the read of rowids alone hold a long value. The reader looks at the column names of both tables first, in the list that holds generated and hidden columns too (`pragma_table_xinfo`; the plain list leaves them out, which the fourth review found), which loads no row, and answers `db-rowid`: `Far::Rowid`, "state.db declares a column that hides its row numbers". Hermes's schema declares none (third review, finding 2; fourth review).
- **For ticket 37: a paged read by rowid passes over rows that move below its cursor.** Hermes's `sessions` table keeps its rowids through a VACUUM, because its text key gives it an index. A table with no index at all, which the reader accepts, is renumbered by one, and a row can be inserted below the cursor between two reads. Either way a row that lands below the cursor is not read in that sweep, and the next whole sweep reads it. No healthy row is marked skipped by it. This is true of any paged read by rowid (fourth review, a note).
- **No page is asked from a rowid below zero.** The caller refuses to send one, the far program refuses one from anyone, and the checker takes no number below zero in any answer's last line (second review, finding 3).
- **Statuses.** 0: it said what it had to (an answer, "busy", "too large", "no database", "sqlite-old"). 1: it crashed, with one line on standard error that holds no row text. 3: the deadline. 4: its channel was gone. 5: too much memory. 127: the far shell found no `python3`, which with a Python that has no `sqlite3` module is `Failure::NoHistory`, "no history on this machine".
- **Every number of an answer's last line is checked, for every kind of answer.** A probe and the held file count nothing; a sessions read counts sessions and usage rows and no page; a page of fingerprints counts fingerprints, the rows looked at and the last rowid, which is past where the page began by at least one for each row (finding 3).
- **Nothing is logged but kinds, counts, times and statuses.** The log sink given to `Reader::new` gets one line for each read and each wait. Session ids are not logged.
- **A far profile whose gateway is stopped shows no history until that gateway runs again, where the far Python has Apple's SQLite.** A database in write-ahead mode has no `-wal` and no `-shm` file once Hermes has closed it. The reader opens a database one way only, through a connection that cannot write (`mode=ro`), and never as a database that cannot change, which the design rules out. Apple's SQLite (`/usr/bin/python3`) will not open such a database that way (measured: "unable to open database file", and no file made), so the read fails as `Far::Open`, "state.db could not be opened", and nothing of that profile is read. While the gateway runs, both files are there and the read works. A SQLite other than Apple's opens it and leaves a `-wal` and a `-shm` file behind.
- **A read-only open can still make files beside the database.** Where the database's `-shm` file is missing and its `-wal` is there (a log left by a writer that did not close), SQLite makes the `-shm` file to read the log, and the rows that are only in the log are read. That is the spec's "no intentional write", never "nothing written".
- **Not verified here:** Linux; a real SQLite older than 3.43 (the refusal is tested with the system's Python made to say it has one); a far machine other than this Mac behind the lab's `sshd`; a real 3 GB database (ticket 37 measures the Mini). The time of a read in the lab is 0.35 to 0.7 s, nearly all of it Python starting.

**What the check on the listener proves, and what it does not.** After it connects, the relay asks the kernel which user the listening process runs as (`getpeereid` through `ctypes` on macOS, `SO_PEERCRED` on Linux) and sends nothing unless it is the login user. That proves the listener runs as the login user, and it catches a listener of any other user. It cannot tell two processes of the same user apart: a second process of that user that takes the socket's place is accepted (`checks::a_second_listener_of_the_same_user_is_accepted_which_is_the_boundary`). Same user on the far machine is the trust boundary, as it is for Hermes's own client and for phase 1 on this Mac. An SSH login as that user is not a stand-in for the check; it is what makes the relay run as that user.

What a caller must know:

- **Only `Request` can be asked.** `Far::exchange` takes one, and the relay itself refuses a line whose verb is not `identify` or `session-ticket`, so a mistake on this side cannot pause a far gateway. A route is handed a line (`Route::exchange`): `Request::of` gives the request that line is, and none for a line that is not one of the two exactly as this side writes them.
- **A home is a canonical far path**, as `Far::homes` gives it. The relay refuses any other spelling (`home-not-canonical`), so one folder is never asked under two names. `Homes::root` is the text `machine_key` needs.
- **The checks are made on open descriptors.** The relay opens the home once, checks that descriptor, and finds the socket from it (a look-up in that folder, then a connection made from inside it). A path that is swapped for another after the check leads nowhere new (`checks::a_path_swapped_after_it_was_opened_does_not_change_what_was_checked`).
- **Where a check cannot be made, the machine is not covered.** No `python3`, no way to ask the kernel who listens, a home someone else may write, an access control list that cannot be read: each is `Unchecked`, by name. Hermes's own client falls back to the path checks where the kernel cannot say; the relay does not.
- **"Closed to others" is the mode bits and the access control list.** On macOS a list can let another user write a folder whose mode is 0700, and Hermes's own client reads only the mode there. The relay reads the list of the home, the socket, the pointer file and the folder it names (`acl_get_fd_np` and `acl_get_link_np` through `ctypes`). A home's list may let someone else read it, as mode 0755 may, and nothing more; the other three may allow no one else anything. An entry that denies opens nothing, and the user's own entries do not count. A list that cannot be read, or holds an entry the relay cannot make out, is `permissions-unread`. On Linux no list is read: a POSIX list's reach is bounded by the group bits, which are checked. On any other system the relay refuses (`lists::`).
- **The relay's deadline is its own.** `Far::new(seconds)` is how long it lives on the far machine, 10 to begin with; a watchdog thread ends it then whatever it is doing, and the kernel's alarm two seconds later if the thread never ran. This side waits two seconds longer than that. `Silent::CutOff` means this side stopped waiting and the relay may still run: until that deadline has surely passed, `exchange` for that home returns `Silent::Busy` and starts nothing. Other homes are not held up.
- **The discovery command has a deadline too** (15 s, a watchdog in the shell), and is held back the same way after a cut-off.
- **An answer is at most 512 KiB**, the size Hermes's own client stops at; a longer one is `Quiet::TooLong`.
- **A ticket is in an `Answered` and nowhere else.** `Answered` prints as `Answered(<masked>)`. No error holds any of the relay's output, and its standard error is never read. Pass the answer to `granted`, which gives a `Ticket` that does not print either.
- **`python3` runs as `python3 -I -S -B -`**: apart from the user's own Python settings and packages, and writing no bytecode. Nothing is written to the far disk by intent, by the relay or by Python for it.
- **A machine with more than 200 profiles is not covered** (`MOST_PROFILES`, `NotCovered::TooManyProfiles`), and neither is one whose homes command prints more than 256 KiB. The homes are asked one after another, so there is a bound, and a machine over it is refused whole: discovery never gives some of the homes as if they were all of them. Folders that lead to one home count once, before anything is counted (`discovery::v_discovery_never_silently_drops_a_valid_home`).
- **A check that fails for any home makes the machine not covered**, with the reason and the home. A home with no socket, or a gateway that is not running, is `Quiet::Absent` in the picture and uncovers nothing. A link lost on the way gives `NoPicture::Unreached`: nothing is known and nothing should change.
- **`Picture::contested`** lists homes that two instances both say they serve, which is a restart overlapping.
- **Not verified here:** Linux (`SO_PEERCRED` and `/proc/self/fd`, the same code, never run), a far Python older than 3.9 (it lacks `fcntl.F_GETPATH` and falls back to resolving the path), a far home on a file system that ignores letter case and is named in another case than its folder (refused as `home-not-canonical`), an NFSv4 access control list on a Linux far machine (only the mode bits are read there), and a far login shell other than zsh.

## Updating from upstream

Remotes: `origin` is this fork, `upstream` is the author's repo with pushing disabled.

1. Fetch both remotes: `git fetch upstream && git fetch origin`.
2. Fast-forward the fork's `main` to upstream: `git push origin upstream/main:main`. This must be a fast-forward. If it is refused, someone committed to `main`; move that commit to `fork` first.
3. Bring `fork` up to date by merging, not rebasing: `git checkout fork && git merge --ff-only origin/fork && git merge origin/main`, fix any conflicts, then `git push origin fork`. Merging keeps `fork` history stable, so open ticket branches built on it stay valid and no force push to a shared branch is needed.
4. Run the checks:

   ```sh
   pnpm install --frozen-lockfile
   pnpm run format
   pnpm run check
   pnpm run test
   pnpm run lint
   cargo test --workspace
   git diff --check
   ```

5. Rebuild and reinstall: `sh src/tooling/fork-install.sh`. It builds the bundle with the fork's overlay and `AGENT_HUD_HOOK_OWNER` set to the installed copy's executable (so its client hooks switch works), quits the running fork, replaces `/Applications/Agent HUD Fork.app` and opens it (`--no-open` skips that). It always builds in this checkout's own `target/`: a build folder shared between worktrees can reuse another worktree's crates.
